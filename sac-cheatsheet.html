Side 1 · Practices & Risks

The linkage moves that carry the top band

Almost every Very high descriptor asks you to connect back to something. If a section names none of these, it is capped below Very high however correct it is.

KS1→ the organisation's goals and objectives
KS2→ impact on the organisation (money, contracts, notification)
KS3→ criteria applied, measured, documented
KS4→ viable resolutions, named back to an Act or framework
KS5→ Med: legal obligations · High: goals & objectives · V.high: industry frameworks

Before submitting, highlight every goal, objective, Act and framework you have named.

Goals vs objectives — get this right first

Both KS1 and KS5 are capped below the top band unless you name these and link back to them. They are not the same thing, and markers check.

GoalObjective
ScopeBroad direction — what the organisation is trying to becomeA specific step towards that goal
WordingQualitative, long-term, no numberMeasurable and usually time-bound (SMART)
TestCould two people disagree about whether it was met?Can you put a number or a date on it?
Example"Become the leading provider of fleet software in Victoria""Win three government contracts this financial year"; "99.9% uptime"

Finding them in a case study. Goals sit in the opening paragraphs — "small but fast-growing", "taking on more high-profile clients". Objectives appear wherever there is a figure, a percentage, a deadline or a contract target.

If no measurable objective is stated — which is common — say so explicitly and infer one that is consistent with the goal: "No measurable objectives are stated; an objective consistent with this goal would be achieving the security posture high-profile clients require during procurement." That inference is not padding — every KS1 and KS5 linkage hangs off it.

Objectives are what make a security failure quantifiable — an outage breaches a stated uptime objective; a failed security questionnaire costs a named contract. That is how a vulnerability becomes an impact rather than an observation.

KS1Analyse the current practices

Four things to cover: goals and objectives · in-house vs external development · security controls · threat modelling principles. If no measurable objectives are stated, say so and infer one — without a goal to link to, KS1 and KS5 are capped.

In-house: control of delivery, domain knowledge and client relationships stay inside and changes are cheap — but there is usually no specialist security capability, which is why nothing gets vetted, patched or reviewed. External: buys that capability and scales quickly — but adds third-party exposure, IP and licence questions, and contractor practices nobody verifies.

The six security controls → what each closes

For each: does the organisation have it, how does it protect the practice and the data, and later — recommend it where missing.

IAM has four parts — multi-factor authentication · role-based access on least privilege · prompt deprovisioning · logging and review. MFA = two different kinds of evidence: something you know / have / are, so a phished password alone is not enough.

Encryption has two states — in transit (TLS) and at rest. Case studies often have one and not the other: "TLS on the portal but an unencrypted production database".

A control they have but do not enforce is worth more marks than one they simply lack.

Threat modelling — the three principles

Named in the Medium, High and Very high descriptors of KS1, and in every band of KS5 from Medium up. If your response never uses the phrase, you have capped yourself.

PrincipleAsk the case studyUsual finding
1. Define security requirementsWere they written down before building?Absent — issues fixed as customers report them
2. Identify & mitigate threatsSystematic, or reactive?Reactive — no risk register
3. Confirm mitigationIs anything audited, tested, reviewed after?Absent entirely

A control designed but never verified is not a mitigation, it is an assumption. Principle 3 is the one almost every organisation skips — saying so is free marks.

Because they perform none of the three principles, their controls were not chosen against identified threats — they accumulated by habit. That is why the risk that actually materialised had no control at all.

KS2Vulnerability, threat, risk

The descriptors use all three and markers notice when they are treated as synonyms.

VulnerabilityA weakness in a system or practice
ThreatSomething or someone that could exploit it
RiskA threat exploiting a vulnerability, with a likelihood and an impact

A vulnerability is a fact. A risk is a judgement — and judgements are what get marked at the higher bands.

The ten vulnerabilities — why each is a risk, and what plants it

Naming the weakness is the bottom band. The middle column is where the marks are: what an attacker actually gains, or what actually breaks. The right column is what to look for in the stimulus.

WeaknessWhy it is a security riskSignal phrases in the case study
1. Use of APIs The API's security, availability and pricing become yours. Data leaving the organisation engages APP 8 if processed overseas, and a change to the API breaks your product without warning "integrates a third-party service", "cloud-based", "sends requests to"
2. Malware Source code stolen or encrypted; credentials captured. A compromised build machine can inject malicious code into the product itself, which then ships to every customer "clicked a link", "downloaded an attachment", "systems were encrypted", a found USB
3. Unpatched software A released patch announces the vulnerability it fixes — the gap between release and deployment is documented, automatable exposure. Two of the Essential Eight address this alone "two versions behind", "updates applied when there is time", "not restarted in months"
4. Poor identity & access management A shared credential destroys accountability — you cannot tell who did what. Password-only means one phished credential is full access; excessive permissions mean one compromise reaches everything "the team shares a login", "no MFA", "still has access", "everyone has admin"
5. Man-in-the-middle Credentials, code and customer data are read in transit — and the attacker can alter what is delivered (the changed invoice, the modified package download) "public Wi-Fi", "no VPN", "unencrypted connection", "the invoice details had changed"
6. Insider threats Already past the perimeter controls: can exfiltrate code or data, weaken configuration, or introduce malicious changes that look routine. Need not be malicious — copying the live customer table into a test database for realistic data is a careless insider threat, and that is usually what has happened "a developer changed the configuration", "copied the data", "took files when they left"
7. Cyber security incidents Something already compromised — proof the risk is real rather than theoretical. This is your evidence of impact for the top band of KS2. Use it any breach, infection or outage already described
8. Third-party software Runs with your product's privileges, so its vulnerabilities become yours — a supply-chain risk. Its licence terms bind you under the Copyright Act 1968: open source is licensed, not obligation-free "a free library", "open-source component", "nobody checked the licence"
9. Ineffective code review Defects, insecure patterns and hard-coded credentials ship unexamined, and a malicious change made through a compromised account passes unnoticed. Unrecorded reviews cannot be evidenced to a client or auditor even when they happened "merged as soon as it compiles", "reviews when there is time", "no record is kept"
10. Combined dev / test / prod Usually the most serious finding — it multiplies every other weakness rather than sitting beside them. See the box below "all on the same server", "the test database contains live data", "work directly on the live site"

Three moves, three bands, for every one of them: name it in study-design language (Very low) → explain the mechanism from the middle column (High) → state the organisational impact (Very high). Go deep on three or four rather than shallow on nine.

Combined dev / test / production — why it is the worst one

Usually the most serious finding in a case study, and the one to go deepest on, because it multiplies every other weakness rather than sitting beside them.

  • No gate before live. Untested code reaches the production system without a deliberate promotion step, so a defect or a malicious change goes straight to customers.
  • Real customer data ends up in development, where protections are weaker and far more people have access than their role requires. That is an APP 6 breach (used for a purpose other than the one it was collected for) and an APP 11 breach (not reasonably secured), before any attacker is involved.
  • The blast radius becomes the whole business. A compromise of any development machine — one phished developer, one unpatched laptop — reaches production directly. The weakest machine in the organisation sets the security of the live system.
  • No separation of duties. Whoever writes the code can deploy it, so there is no point at which a second person must agree.
  • Updates cannot be trialled safely, so patching itself becomes risky — which is often why the same organisation is also behind on patches. The two findings are causally linked; say so.

The fix, in recommendation form: distinct infrastructure per environment · de-identified or synthetically generated test data · deployment as a deliberate promotion between environments, not a save. The ISM names this specifically in its Guidelines for Software Development.

KS2's top band asks how the vulnerabilities impacted the organisation. All five — most students stop at the first.

KS3Criteria — propose, then apply

The Medium/High line is the word applies. Medium proposes criteria and says how they could be measured; High runs them against the case study and reaches a verdict; Very high adds accurate measurement, documented clearly.

Three parts, or you lose a band: the question (answerable yes / partially / no) · the measure (what you count, compare or inspect) · the data source.

Weak: "Is the code secure?" — unanswerable, so it cannot be applied. Strong: "Is all code reviewed by a second developer before release?" · proportion of merges with a recorded reviewer · repository merge history.

A criteria set that covers the outcome

Pick five or six matching what the case study actually describes.

Criterion (as a question)Measure · source
Are dev, test and production separated?Shared hardware? prod data in non-prod? · architecture docs
Is repository access restricted to current, authorised staff?Accounts vs staff register; MFA enrolment · audit logs
Is all code reviewed before release, and recorded?Merges with a named reviewer · merge history
Are OS and applications patched promptly?Mean days release → deployment · patch records
Is personal information encrypted in transit and at rest?TLS enforcement; DB encryption setting · config
Are security requirements defined and verified?Security requirements in the SRS; any audit · SRS, reports
Do developers complete secure-development training?Completion rate; phishing click rate · training records

Document it as a table, one verdict per row

Use three verdicts: met / partially met / not met. "Partially met" is right whenever a practice exists but is not enforced, not recorded, or covers only part of what it should — which describes most real organisations.

Six criteria were applied and none was fully met: three failed outright, three partially. The failures cluster into environment separation and access management, which together account for the entire incident chain. Current practices are therefore not effective at protecting the development process or the data.

KS4Legal and ethical

Most students write only the legal half, so the ethical half is where marks are easiest to gain.

Legal — source: an Act of Parliament · test: did they break the law? · consequence: investigation, penalty, enforceable undertaking.
Ethical — source: professional and community expectations · test: was it the right thing to do? · consequence: reputational damage, loss of trust, censure.

The strongest examples are both at once, because you can analyse them twice.

Privacy Act 1988 (Cwlth) — the named APPs

APP 1Open and transparent management — a clear, current privacy policy
APP 3Collect only what is reasonably necessary
APP 6Use or disclose only for the purpose collected (prod data used for testing; data pasted into an AI tool)
APP 8Reasonable steps before disclosing overseas (offshore API or cloud)
APP 9Do not adopt government-related identifiers as your own
APP 11Secure personal information, and destroy or de-identify it once no longer needed

APP 11 is the workhorse. "Reasonable steps" scales with the sensitivity of the data, the harm a breach would cause, and the organisation's size and resources — which is what makes it arguable, and arguable is what the discussion bands want.

For a company holding licence numbers, reasonable steps under APP 11 would clearly include encryption at rest and MFA — both inexpensive and standard. They had neither, so this is not a marginal judgement call.

Notifiable Data Breaches scheme

Breach likely to cause serious harm and not remediated → notify affected individuals and the OAIC as soon as practicable. The delay is a separate breach from the original failure, and it is legal and ethical at once — both halves of KS4 in one example.

The other instruments

Privacy and Data Protection Act 2014 (Vic) — Victorian public sector and contracted service providers handling their data. A state government client makes it relevant, and most students miss it. IPPs 1, 2, 4, 5, 9 — IPP 4 (data security) is the counterpart of APP 11.

Copyright Act 1968 (Cwlth) — protects the expression of ideas, including source code; automatic, no registration. Appears as a library used outside its licence (open source is licensed, not obligation-free), or AI-generated code reproducing training material.

Legislation binds by law — penalties, investigation, enforceable undertakings. Frameworks are not law, but bind contractually the moment a client writes one in; failure costs contracts and audits.

The four ethical issues

  • Ineffective security practices. Those exposed had no way to assess the risk and no realistic alternative — that asymmetry places a heightened obligation on the organisation, independent of the law.
  • Use of AI in development. Over-reliance — losing the ability to review, debug and maintain (this is the ethical issue, not AI use itself) · data disclosure to a third party · provenance · accountability — "the AI wrote it" is no answer to a regulator.
  • Intellectual property. Who owns the code, designs and data; open-source licence terms; IP settled in the contract when development is outsourced.
  • Copyright. Images, code, libraries or fonts used without a licence.

Two more that case studies plant

Disclosure and transparency — delaying or downplaying a breach to protect reputation. Usually the strongest available: the harm is concrete and it is also an NDB breach. Real customer data in development — APP 6 and APP 11 legally; ethically, they consented to a service, not to a test database.

Writing the ethical half

Four moves: name the issue → explain why it is ethically problematic (who is harmed, and how) → apply it to the case study → consequence, legal and non-legal.

Resolutions must be viable — name what changes, who does it, which obligation it satisfies. "Be more ethical" is not a resolution; "an incident-response plan naming a breach assessor, with a 72-hour escalation deadline" is.

KS5Recommend and justify

All three top bands want the same three ingredients — security controls, threat modelling principles, improvement strategies. Only the linkage changes:

Mediumrecommends + describes feasible methods → legal obligations
Highanalyses their impact → goals and objectives
Very highjustifies them → industry frameworks

Hit all three linkages and you have covered every band above Low.

The two named improvement strategies — both must appear

1. Onboarding / induction and ongoing developer training. Policies and why they exist; what data may be used in development; credentials; what may go to AI assistants; secure coding, review and phishing; refreshers, not one session on day one. Why it works: most incidents involve human behaviour, not a control failing — training addresses the cause, controls contain the symptom.

2. A documented risk management plan. Identifies each risk · rates likelihood and impact · assigns a mitigation · names an owner · sets a review cycle. Why it works: survives staff turnover and produces what an auditor asks for.

Mitigation menu — match it to what they actually have

Recommending a control for a problem the organisation does not have reads as a memorised list.

VulnerabilityMitigation
Combined environmentsSeparate infrastructure; de-identified or synthetic test data
Poor IAMIndividual accounts; MFA; least privilege; deprovisioning; access logs + review
Unpatched softwareDefined schedule with a maximum deployment window; automation
Ineffective code reviewMandatory second reviewer enforced by the tooling, and recorded
Third-party softwareVet dependencies before integration; licence register; monitor advisories
MalwareApplication control; anti-malware; app hardening; restrict admin
Man-in-the-middleEnforce TLS everywhere; VPN for remote access
Insider threatsLeast privilege; logging and monitoring; separation of duties; offboarding
Unmanaged AI assistantsWritten AI-use policy: what may be shared, human review, provenance
Data retained too long / no verificationRetention schedule with secure disposal; scheduled access reviews, application security testing, audit-log review

Sequence them, and say why

1. Contain the biggest exposure — environment separation, production data out of development. 2. Close the entry point — IAM, because most incidents begin with a credential. 3. Stop the recurrence — enforced code review, patching schedule. 4. Make it durable — threat modelling in the lifecycle, training, risk management plan. 5. Verify — audits, access reviews, re-run your Section 2 criteria.

Step 5 is the one almost nobody writes — and it is explicitly the third threat modelling principle. Ending with how they will confirm the mitigations worked closes the loop on your own evaluation.

The two frameworks

Essential Eight (ACSC): application control · patch applications · configure Office macro settings · user application hardening · restrict administrative privileges · patch operating systems · multi-factor authentication · regular backups. Maturity levels 0–3 — contracts often specify "Maturity Level 2".

ISM (ACSC) — Guidelines for Software Development, three named: development, testing and production environments (separated; no production data in dev/test) · secure software design and development · application security testing. These map onto the most common SAC findings — usually the strongest framework to cite.

Sentence frames

KS1 → goal. This practice supports the objective of … because … KS2 → impact. This vulnerability allowed … which resulted in … costing the organisation …

KS3 → verdict. Applying the criterion "…", the evidence shows … therefore this is partially met.

KS4 → both halves. Legally this breaches … under …; ethically, the harm falls on … who had no say in it.

KS5 → framework. Implementing … addresses …, satisfies … under …, and aligns them with … (Essential Eight / ISM), which the contract requires.

Name what the risk threatens

A cyber security incident is an event that has actually compromised one of these three — saying which sharpens a vague answer instantly.

ConfidentialityOnly authorised people can read it — encryption, IAM, least privilege
IntegrityData and code are not altered without authorisation — code review, version control, TLS
AvailabilityIt is there when it is needed — backups, patching, separated environments

Chain the weaknesses together

Single findings read as a checklist. A chain reads as analysis, and it is what the Very high bands of KS2 and KS3 are describing:

phishing email → credential taken (no MFA) → repository reached (shared login, no deprovisioning) → production data reached (combined environments) → data readable (no encryption at rest) → notification delayed six weeks (no incident plan).

Every link is a separate named vulnerability, and a place one control would have stopped it — which is how you justify the sequence of your recommendations.
